# 056 — What pii costs under load and over time (spec 110, P5)

**Date**: 2026-10-10. **Measurement only** — no source, threshold, cap or default was changed. Findings are filed
at the end with their numbers; each needs its own spec.

## Setup (applies to every number below)
- Binary: `target/debug/pii` (**debug build**, unoptimised) at the spec-109 tree. Host: single machine, shared —
  load average ~15 during the work (other tenants: ffmpeg, python sidecars, ollama). Daemon `--sandbox off`,
  empty config, default worker threads (4) and blocking cap (8).
- Model: **scripted** (`PII_MODEL=scripted:<400k×{"text":"ok"}>`), so the provider is not the variable. Limit:
  this removes all real model latency, network and token cost; what is measured is the engine's own overhead.
- Workload: graph `starter/loadagent` = one `agent` node (1 scripted turn, no tools) → `transform`. Each run is
  8 journal events. The graph lives in the scratch runtime dir, not in the repo.
- Driver: a Python asyncio client over the real UDS + `sys.hello` handshake (`pii soak` prints totals only, no
  percentiles). N connections, each looping `run.start` then polling `run.get` until `succeeded`/`failed`.
  Poll interval 10 ms (so run-lifecycle latency from the client has ±10 ms quantisation).
- Sources: **C** = client wall clock (`perf_counter`); **S** = server-side `dur_ms` from `run.list`;
  **H** = `pii health --json` / `sys.status` (`rss_kb`, `counts`, store bytes); **M** = `pii metrics`;
  **P** = `/proc/<daemon pid>/{stat,io}` (CPU seconds, `wchar`, `write_bytes`, threads).
- `pii metrics` exposes **no latency histogram and no RSS** (counters/gauges only), so every percentile below is
  from C or S, never from `pii metrics`. RSS comes from H.

## R2 — The instrumentation bill (60 s × 8 conns, 3 rounds per config, order rotated, fresh store each)

- Trajectory: the cost is visible in CPU (+10.6%) and bytes, not in latency or throughput.
- Log file: below resolution on everything except its own on-disk size (300 B/run).
- Observer attached vs `NullObserver`: **no switch exists** in `pii daemon` (`cmd_daemon.rs` always wires
  `ContractObserver`/`DenialObserver` over the fan-out; `NullObserver` is only the Engine's unattached default).
  Not measured; not faked. The audit log (always on) cannot be turned off either, so the baseline includes it.
- Health polling cost: `sys.status` p50 3.5 ms, p99 30 ms under load (R1) — measured as an RPC, its CPU share is
  not separable at 15 s polling.

## R3 — Soak (trajectory ON + log file ON + audit; 4 connections)
- **Actual duration: 32.67 min of daemon uptime** (target ≥30 min met), delivered as four foreground chunks
  (460 + 3×480 s of load; gaps of seconds between chunks while the next call was issued). 85 018 runs, 0 failed,
  0 errors, ≈44.5 runs/s steady (chunks 2–4: 44.4 / 44.7 / 44.4). Run p50 85.5 → 87.1 → 87.4 ms, p99 145 → 148
  → 152 ms (C) — mild upward drift, not a cliff.
- **Gap, stated plainly**: a driver bug (`--no-runls` path) crashed chunk 1 at its end, so chunk 1 has **no 30 s
  samples and no latency table** — only the before/after `pii health --json` (H) and the final disk sizes. The
  RSS series below is therefore: chunk-1 start and end from H, then 30 s samples for the remaining 24 min.
- RSS (H, `rss_kb`): start **60 468** (0 runs) → 8.0 min **76 484** (20 929) → 16.0 min **79 740** (42 249) →
  24.0 min **83 136** (63 710) → end **86 372** (85 018 runs, 32.7 min). After 20 s idle: 85 972 (no drop).
- Growth on disk / in the store: main store 1.06 MB → **216.6 MB** (2.5 KB/run, never shrinks); journal events
  680 144 (8/run, M `pii_journal_events_total`); trajectory dir **195.97 MB in 85 019 files** (2.3 KB each);
  log file 4.4 MB + `pii.log.1` 10 MB + `pii.log.2` 10 MB (**rotated twice**; 10 MiB × keep 5 default bounds it at
  ≤ 50 MiB); `audit.log` 279 B (unchanged). Bytes written by the daemon: ~3.0 GB per 8-min chunk
  (`write_bytes`, 125–130 KB/run); CPU 522–531 s per 480 s chunk (~1.1 core).
- Descriptors/threads at end: 8 fds, 9 threads (flat).
- **Leak verdict: RSS trends up with runs completed, linearly, with no plateau.** Least-squares over the 48 samples
  gives **+152 KB per 1 000 runs (~155 B/run)**; the last half of the series alone gives +159 KB/1 000 runs, so
  it is not a warm-up transient. +25.9 MB over 85 018 runs. The 300 s baseline of R1 shows the same slope after
  warm-up (74.2 → 75.3 MB over ~8k runs, ~140 B/run) so it is not caused by the trajectory/log sinks. Threads and
  fds are flat, so it is heap/cache growth keyed to runs, not a handle leak. At the measured ceiling (45 runs/s)
  that is ~25 MB/hour; at an operator's realistic rate it is negligible, but it is monotone and unbounded as
  measured. **What 33 minutes does not prove**: whether it saturates beyond ~85k runs (the in-memory run table,
  `RUN_JOURNAL` read cache or per-run sink state are candidates — **not investigated**, measurement only), nor
  any behaviour over days.

**Dominant term: the model — 99.9% of the wall time** (≈ 28 s per model turn here; the agent made 2–3 tool calls,

is multi-turn on a CPU-only 3B with the host at load ~15. The ratio (model ≫ everything else) is the stable result;
the absolute seconds are host-dependent. An earlier probe with a missing file looped on `glob`/`fs_read` for >2 min
(agent behaviour on a not-found, not an engine hang) and was killed by me.

## R5 — The gate's coverage cost (spec 108), same tree, warm `target/`
| mode | exit | wall | disk added | volume free |
|---|---|---|---|---|
| `QG_SKIP_COVERAGE=1 bash quality-gate.sh` | 0 | **92 s** | ~0 (target 89.47 GB, unchanged ±1.6 MB) | 19.35 GB → 19.35 GB |
| `bash quality-gate.sh` (coverage measured: 77.66% ≥ 74.0) | 0 | **169 s** | **+7.84 GB** (`target/llvm-cov-target`) | 19.35 GB → 11.45 GB |

The ratchet costs **+77 s (+84%) and 7.3 GiB** per gate run, on top of a warm cache for everything else (the
instrumented build itself starts cold). Order: skip-mode first, full second. A note on the export (see F7):
`cargo run -q -p xtask -- fresh-gate --worktree` **without** `QG_SKIP_COVERAGE=1` exhausted the volume.
With `QG_SKIP_COVERAGE=1` it printed `fresh-gate: PASS` in 233 s with 10.9 GB free at export.

## Findings (filed, not fixed)
- **F1 — `run.get` answers NotFound for an in-flight run**: 128 054 NotFound polls for 12 452 runs (10.3/run, i.e.
  for the whole run until it finishes). A client cannot tell "not yet" from "unknown id"; `pii soak` papers over
  it by ignoring errors. (A run that failed validation at start also stays NotFound forever; observed in the
  smoke runs: `V2 … capability … not granted`, then `run.get` NotFound, so `pii soak` would spin to its 60 s poll cap.)
- **F2 — RSS grows ~155 B/run with no plateau** over 85 018 runs (+25.9 MB, R3), baseline config included.
- **F3 — write amplification**: the daemon writes ~125–131 KB per run (`write_bytes`) to retain 2.5 KB in the
  store (~50×); ~3 GB per 8 minutes at 44 runs/s.
- **F4 — trajectory has per-run caps only**: one file per run, cap 10 000 events / 16 MiB per run (never reached:
  2.3 KB/run), **no aggregate cap or retention** — 85 019 files / 196 MB in 33 min (~390 MB and ~160k inodes per
  hour at the ceiling). The log file IS bounded (rotated twice, 10 MiB × 5).
- **F5 — the store never shrinks**: 216.6 MB / 85k runs; `pii_store_bytes` is the only visibility.
- **F6 — throughput ceiling ~45 runs/s ≈ 1 core** (23 ms CPU/run, debug build); `run.start` p50 48 ms at 8 conns
  vs 19.8 ms at 4 — queueing, not parallelism. `pii metrics` has no latency histogram or RSS, so none of this is
  visible from the product surface.
- **F7 — the gate's coverage step and `fresh-gate`**: the fresh-gate disk guard is 2 048 MB
  (`FRESH_GATE_MIN_FREE_MB`) but a coverage-measuring export needs ≥ 11.4 GB; with 11 GB free it ran the
  instrumented build inside the export and **took `/projects` to 0 bytes free for ~3 min** (ENOSPC in the export;
  the failed export dir is left behind, 11.4 GB). It does not skip coverage by itself; `QG_SKIP_COVERAGE=1` must
  be set by the caller.
- **F8 — no NullObserver switch / no way to disable the audit log** in `pii daemon`, so the R2 observer A/B
  cannot be run as specified.
