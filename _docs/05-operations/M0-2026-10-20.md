## 2026-10-20 late (11:30-11:35Z) — the third gate, and the design answer

The verdict of record for the DIRECT path is unchanged (`M0 REFUSED`), but the refusal is now measured

### Gate 3: podman cannot set up its rootless user namespace inside the landlock domain

Reproducer extended with the podman state dirs and `/dev/shm` (the lnx `workspace` grant, plus a
must-fail write-outside probe that printed `RESTRICT OK` on every run below):

| # | grant | podman's result | rc |
|---|-------|-----------------|----|
| control | none | `run --rm localhost/pii-agent:1 true` | 0 |
| 1 | daemon grant | `failed to open 2048 locks in /libpod_rootless_lock_1000` (spec 229) | 125 |
| 2 | + rw `/dev/shm` | `cannot re-exec process to join the existing user namespace` | 1 |
| 3 | + rw `/dev/shm`, fresh podman state | `newuidmap: write to uid_map failed: Operation not permitted` | 125 |

Discriminating runs (same binary, same image, only the confinement varied):

    unshare --user --map-root-user true        grant: EACCES on /proc/self/uid_map   | control: rc 0
    unshare --user --map-root-user true        grant + rw /proc/self: rc 0
    newuidmap <pid> 0 1000 1 1 100000 65536    grant + rw /proc: open ok, write EPERM
    newuidmap <pid> …                          grant + rw /proc/self: open EACCES
    newuidmap <pid> …                          no landlock, NO_NEW_PRIVS only: write EPERM

So: the sandbox can create a user namespace that maps only its own uid, and cannot complete the
subordinate-range mapping rootless podman needs. Granting `/proc` read-write lifts landlock's *open*
denial and the write is then refused at the credential layer (`Operation not permitted`), which is where
landlock's mandatory `no_new_privs` and the setuid `newuidmap`/`newgidmap` helpers meet. This is not a
missing path grant: **rootless podman cannot initialise inside a landlock domain**, and a further grant
cannot buy it (spec 229 R2 anticipated exactly this outcome).

### The delegated runtime: measured, and it works

An out-of-sandbox runtime is already running on the host: `podman.socket` is active and
`/run/user/1000/podman/podman.sock` is the API. A process confined by the daemon's exact grant talks to
it — landlock does not mediate `connect()` — and starts a container through it:

    # ping, confined:                     HTTP 200
    # POST /containers/create             {"Id":"6647d870bf1a…","Warnings":[]}
    # POST /containers/{id}/start         HTTP 204
    # POST /containers/{id}/wait          0
    # GET  /containers/{id}/json          "ExitCode":0
    # DELETE /containers/{id}             HTTP 200

Every one of those calls was wrapped in the grant replica, whose write-outside probe printed
`repro: RESTRICT OK (write outside grant refused: Permission denied)` — the confinement was in force.
The podman CLI's own `--remote --url` redirect was NOT run: the session's policy hook requires a human
approval for that form and none is available. The API calls above are the same measurement by its
protocol.

### Conclusion

- M0 stays **REFUSED** for the current design (the coder node execs podman inside the sandbox): three
  measured gates, the last one structural.
- The container design is **viable by delegation**: the daemon keeps its landlock domain and starts the
  container through the runtime's API socket, where the container — not the landlock domain — is the
  isolation boundary. Filed as spec 230 / row A98.
- No `coder.spawned` has been journalled for a container path by any daemon on lnx. The coder demo
  (`/tmp/pii-ws-3aQWp1`) remains blocked until spec 230 is implemented and M0 re-run.
